# Project Memory

_Facts, conventions, and patterns discovered about this project._

---

- **Architecture:** The homepage uses a split-component architecture: WalkerHomepageDesktop (horizontal scroll) and WalkerHomepageVertical (vertical stack) _(Rationale: Desktop uses a custom HorizontalScroll component with sticky positioning and scroll-driven translate, while mobile stacks sections vertically with Framer Motion animations)_ — 2026-06-27
- **Architecture:** Each homepage panel is a pure content component that receives layout wrapping from the orchestrator _(Rationale: Panels like HeroPanel, ValuesPanel, StatsPanel, etc. export their CSS class and content component, while the orchestrator wraps them in HorizontalPage or vertical section elements)_ — 2026-06-27
- **Architecture — Horizontal Redesign Pattern:** Every panel root uses flex-direction: row — no vertical splits (no headers above, no footers below). Text column uses flex: 0 0 25-28% with a fixed min-width. Card elements use flex: 1 1 0 with min-width/max-width clamp ranges and aspect-ratio for height. Panel widths are math-validated against card counts per viewport. _(Rationale: ValuesPanel established the pattern: 28% text + gap + cards. This eliminates all vertical stacking (the original sin of every panel) and guarantees cards never overflow because they're flex-grow-based rather than fixed-width.)_ — 2026-06-27
- **Architecture — Gallery Card Sizing:** Gallery cards use unified sizing: all cards (standard and hero) use height: calc(100% - 8px); aspect-ratio: 4/3; flex: 0 0 auto. No more column-wrap height calculations. The hero/standard distinction is removed — all cards are same size in the horizontal scroll row. _(Rationale: Column-wrap masonry with dynamic 3-row height formulas was brittle and required card-level awareness of grid geometry. The horizontal scroll row is simpler: flex row, nowrap, overflow-x auto. All cards get the panel height and a fixed aspect ratio.)_ — 2026-06-27
- **Research:** Mobile-first design: 72% of web traffic is mobile. Design for phone held in one hand first, then progressively enhance for desktop. The Walker School (our namesake) uses horizontal scrolling on desktop. _(Rationale: Research from PxlPeak, Striped Horse, and NN/g confirms mobile-first is the correct mental model for 2025-2026. The current codebase uses a hard 1100px breakpoint that completely switches between desktop horizontal scroll and mobile vertical stack — this creates two separate experiences rather than one adaptive experience.)_ — 2026-06-27
- **Research:** Modern CSS toolkit for 2025-2026: container queries (@container) for component-level responsiveness, dynamic viewport units (dvh/dvw) instead of vh/vw, :has() selector for parent styling, CSS subgrid for aligned layouts, scroll-driven animations for scroll-linked effects, logical properties for i18n. _(Rationale: Research from MDN, WebKit, peal.dev, and Google Chrome confirms these are baseline features with 95%+ browser support. Container queries are the biggest paradigm shift — they let components adapt to their container size, not viewport size.)_ — 2026-06-27
- **Research:** School website design patterns 2025-2026: The Walker School uses horizontal scrolling (our namesake!). Top patterns: hero video, clear navigation by audience (parent/student/staff), admissions CTAs pinned in header, personalized content, AI chatbots, virtual tours, mobile-first with 67%+ mobile traffic. _(Rationale: Research from Striped Horse's 10 Best School Websites of 2026 confirms horizontal scrolling is an award-winning pattern for school sites. The Walker School specifically is cited as using horizontal narrative journey.)_ — 2026-06-27
- **Architecture:** The site uses a binary 1100px breakpoint: WalkerHomepageDesktop (≥1100px, horizontal scroll carousel) vs WalkerHomepageVertical (<1100px, vertical stack). useIsDesktop(1100) routes between them. Desktop uses custom RAF-based scroll-to-horizontal-translation via HorizontalScroll/HorizontalPage. Mobile uses framer-motion whileInView animations. _(Rationale: This is the core architectural decision that governs all responsive behavior. Any mobile/desktop redesign must work within or modify this split.)_ — 2026-06-27
- **Panel Layout:** All 6 content panels (Values, Stats, Gallery, Testimonials, CTA, News) follow the same desktop pattern: sidebar-left (20-30% width, flex:0 0 X%) + cards-row-right (flex:1 1 auto, flex-wrap:nowrap). On mobile they collapse to flex-direction:column with full-width cards. Hero uses absolute positioning for video overlay. Footer is simple block layout. _(Rationale: Understanding the uniform panel pattern is essential for any redesign — changes to one panel likely apply to all.)_ — 2026-06-27
- **Design System:** CSS variables are the design system backbone: --s-color-_ (semantic), --p-color-_ (primitives), --text-scale: 0.85 global reduction, --text-floor: 0.75rem minimum, --touch-target-min: 44px (mobile), --padding-page: 15px/12px, --spacing-sm/md/lg/xl all clamp()-based. Components use CSS Modules, not utility classes. _(Rationale: Any new CSS must use the existing token system. Do not introduce inline values or bypass the semantic layer.)_ — 2026-06-27
- **Mobile Layout:** Current mobile layout (<1100px) is a collapsed desktop: panels stack vertically with flex-direction:column, cards go full-width, padding adjusts at ≤760px and ≤420px breakpoints. This is NOT truly mobile-optimized — it's just the desktop layout unrolled. Missing: touch-optimized carousels, bottom-anchored CTAs, swipe navigation, mobile-specific content prioritization. _(Rationale: The current mobile experience treats mobile as "desktop without horizontal scroll" rather than a fundamentally different interaction paradigm.)_ — 2026-06-27
- **Mobile CSS:** Use 100dvh (not 100vh) for mobile panel heights. dvh accounts for dynamic browser chrome (address bar) on mobile. Chrome 108+, Firefox 101+, Safari 15.4+. Fallback: min-height: 100vh; min-height: 100dvh; _(Rationale: 100vh on mobile includes the area hidden behind the address bar, causing content to be taller than the visible viewport. dvh dynamically adjusts.)_ — 2026-06-27
- **Mobile CSS:** Use viewport-fit=cover in the viewport meta tag and env(safe-area-inset-\*) for notched phones. Pattern: padding-bottom: calc(env(safe-area-inset-bottom) + constant). On desktop, safe-area-inset values are 0. _(Rationale: Notched phones (iPhone X+) and phones with home indicators need safe area padding to avoid content being hidden behind system UI.)_ — 2026-06-27
- **Mobile CSS:** Use CSS scroll-snap for mobile carousels (scroll-snap-type: x mandatory on container, scroll-snap-align: center on items). This gives native touch swipe + momentum + snap with zero JavaScript. Progressive enhancement: Chrome 135+ has ::scroll-marker() for native dot pagination. _(Rationale: CSS scroll-snap is universally supported, performant (compositor-only), and provides the exact swipe-to-snap interaction users expect on mobile.)_ — 2026-06-27
- **Architecture:** The spec (docs/HORIZONTAL*REDESIGN_SPEC.md) is the single source of truth for layout behavior across all viewports. It defines three tiers (Desktop ≥1100px, Tablet 760-1099px, Mobile <760px) with different interaction paradigms, not just different CSS for the same layout. *(Rationale: Desktop uses horizontal scroll carousel, mobile uses vertical stack with swipe carousels. These are fundamentally different interaction models that share content. The spec governs both.)\_ — 2026-06-27
- **Mobile CSS:** Mobile-first progressive enhancement layers: Layer 0 (semantic HTML), Layer 1 (CSS Grid/Flexbox), Layer 2 (container queries), Layer 3 (scroll-snap, animations with prefers-reduced-motion), Layer 4 (CSS carousel pseudo-elements). Each layer is optional — the base must work without it. _(Rationale: Progressive enhancement ensures accessibility by default. The accessible version is the base. Enhancements are additive, not subtractive. This aligns with WCAG principles and modern CSS architecture.)_ — 2026-06-27
- **Design System:** Use clamp() for all fluid values (typography, spacing, panel widths). Never use fixed px for layout containers. Use fr/% for grid columns. The formula: clamp(min, preferred*vw + offset, max) where preferred scales continuously between breakpoints. *(Rationale: Fluid values eliminate the "uncanny valley" between breakpoints where sizes feel wrong. The human eye is sensitive to typography proportions — continuous scaling maintains visual harmony.)\_ — 2026-06-27
- **Next.js Configuration:** Always configure images.qualities in next.config.ts for Next.js 16+. Default is [75] — any quality prop value not in the allowlist is silently clamped. The project needs qualities: [75, 85, 90, 95]. _(Rationale: Next.js 16 made qualities required. Without it, quality={90} on GalleryCard, ImageCard, and ValueCard is silently rounded to 75. All 71+ photographs render at lower quality than intended.)_ — 2026-06-30
- **Next.js Image Component:** priority prop is deprecated in Next.js 16. Use loading="eager" + fetchPriority="high" for LCP images. Use preload only when the browser cannot discover the image from HTML. _(Rationale: Next.js 16 docs explicitly deprecate priority in favor of preload for the link-rel-preload behavior. However, the recommended pattern for LCP hero images is loading="eager" + fetchPriority="high" — preload is only for undiscoverable images.)_ — 2026-06-30
- **Next.js Middleware:** Exclude next-router-prefetch requests from middleware processing. Skip expensive operations (CSP nonce generation, DB calls) for prefetch requests. _(Rationale: Middleware generates a CSP nonce on every request, including prefetch requests. Adding an early return when next-router-prefetch header is present saves unnecessary crypto operations.)_ — 2026-06-30
- **Architecture Convention:** Custom Link wrappers must expose and forward the prefetch prop to next/link. Footer and secondary nav links should set prefetch={false}. _(Rationale: The custom Link primitive in src/components/primitives/Link/ does not expose prefetch. This means all ~20 footer links and 9 nav links auto-prefetch on viewport entry, wasting bandwidth. Adding prefetch control is low-effort, high-impact.)_ — 2026-06-30
- **Next.js Rendering:** Calling headers() or cookies() in a layout/page forces dynamic rendering, blocking static generation and cacheComponents. Extract to client components or Suspense-wrapped wrappers. _(Rationale: Root layout calls headers() for CSP nonce, which forces every page to dynamic render. This blocks cacheComponents, static generation, and PPR. Must refactor before enabling any caching.)_ — 2026-06-30
- **Component Architecture:** The custom Link primitive in `components/primitives/Link/` must be the single wrapper for all `next/link` usage. Raw `next/link` should NOT be used directly in components. _(Rationale: Centralizes external link detection, variant styling, and future prefetch control. Breadcrumb currently violates this by using raw next/link.)_ — 2026-06-30
- **Architecture:** All content data is static and sourced from `@/data/*` modules, not from a CMS or API. No runtime data fetching exists in the codebase. _(Rationale: The site is a school marketing website with infrequently-changing content. Static imports keep the architecture simple, fast, and zero-dependency for content delivery. This also means the site is almost eligible for `output: 'export'`.)_ — 2026-06-30
- **Testing:** The project uses Vitest for unit tests, Playwright for E2E, and `@axe-core/playwright` for accessibility testing. _(Rationale: Modern, fast test stack with accessibility baked in. Consistent with Next.js 16 recommended testing patterns.)_ — 2026-06-30
- **Security:** CSP nonces are generated per-request in `middleware.ts` using `crypto.getRandomValues()`, passed via `x-nonce` header, and consumed in `layout.tsx` for JSON-LD scripts. _(Rationale: Cryptographic nonces prevent XSS while allowing legitimate inline scripts like structured data. Matcher excludes static assets for performance.)_ — 2026-06-30
- **Image Optimization:** Always use breakpoint-aware `sizes` attributes on `next/image` with `fill`. Use `(max-width: Xpx) Yvw` patterns tuned to the actual CSS layout (not generic values). _(Rationale: Prevents browser from downloading oversized images on mobile; directly impacts Core Web Vitals LCP scores. The DebugBear 2026 guide confirms this is the most commonly overlooked optimization.)_ — 2026-06-30
- **Next.js Configuration:** In Next.js 16, PPR is merged into cacheComponents. Set cacheComponents: true in next.config.ts — do NOT set experimental.ppr separately. The build will error if both are present. _(Rationale: The build failed with `experimental.ppr has been merged into cacheComponents. The Partial Prerendering feature is still available, but is now enabled via cacheComponents.`)_ — 2026-06-30
- **Next.js Rendering:** Do NOT use export const dynamic = "force-static" when cacheComponents: true is set. The build errors: 'Route segment config "dynamic" is not compatible with nextConfig.cacheComponents.' With cacheComponents enabled, the absence of dynamic functions (headers/cookies) makes the layout static automatically. _(Rationale: Build failed with explicit error. cacheComponents handles static/dynamic determination automatically — no route segment config needed.)_ — 2026-06-30
- **Next.js CSP Pattern:** For static sites that need CSP nonces for JSON-LD scripts: use a static nonce from NEXT*PUBLIC_CSP_NONCE env var. Inject the nonce into the script element via a 'use client' component that calls ref.current.nonce = nonce in useEffect. Middleware reads the same env var for the CSP header. This preserves CSP protection without forcing dynamic rendering. *(Rationale: The root layout calling headers() to get x-nonce forced the entire site to dynamic rendering, blocking static generation for 42 routes, Cache Components, and PPR. Since JSON-LD is unchanging static data, a static nonce is acceptable.)\_ — 2026-06-30
- **Security:** All inline <script> tags must carry nonce={process.env.NEXT*PUBLIC_CSP_NONCE ?? ""} to satisfy CSP script-src 'strict-dynamic'. The nonce is a static build-time nonce from the env var (acceptable because the site has no user-generated content). *(Rationale: Without a matching nonce, CSP script-src 'strict-dynamic' silently blocks inline scripts in the browser. This breaks JSON-LD structured data, which degrades SEO rich results. The NonceScript component in layout.tsx already uses this pattern with the same env var. Making components async and using headers() from next/headers breaks in the jsdom test environment — use the env var pattern instead.)\_ — 2026-06-30
- **Architecture:** Three-tier CSS custom property design token system: primitives (--p-_), semantics (--s-_), component (--c-_). Primitives defined ONLY in globals.css. Components reference --s-_ variables. New colors MUST be added to primitives first, then wired through semantics. _(Rationale: Enforces a single source of truth for design tokens, prevents component-to-primitive coupling, and makes theme switching / color migration surgical — change primitives and everything follows.)_ — 2026-06-30
- **Styling:** CSS Modules (\*.module.css) throughout. No Tailwind, no styled-components, no CSS-in-JS. The only global CSS file is src/app/globals.css which defines the design token system and cascade layers. _(Rationale: CSS Modules provide co-location, automatic scoping, and zero runtime cost. The project maintains ~50 module files composing a full design system.)_ — 2026-06-30
- **Animation:** framer-motion is the ONLY animation dependency (no GSAP, react-spring, or Lottie). Three animation strategies coexist: (1) Framer Motion declarative for React components, (2) CSS @keyframes for ambient/detail effects, (3) IntersectionObserver + CSS transitions for scroll reveals. Every animation MUST respect prefers-reduced-motion. _(Rationale: Minimal dependency footprint. Framer Motion handles declarative/stateful animations. CSS keyframes handle ambient effects like aurora drift. The hybrid approach keeps the JS bundle lean while enabling sophisticated animation choreography.)_ — 2026-06-30
- **Responsive Design:** Three breakpoints used consistently across modules: 760px, 420px, 1100px. Container queries (@container) already in use for Card, ImageCard, ValueCard components. Desktop homepage uses dual architecture split at 1100px via useIsDesktop() hook — horizontal scroll on desktop, vertical stack on mobile. _(Rationale: The 760px/420px breakpoints are project convention. Container queries for component-level responsiveness. The desktop/mobile split is not just CSS — it's a React-level architecture decision to swap between entirely different component trees.)_ — 2026-06-30
- **Accessibility:** All Next.js App Router layouts must include RouteAnnouncer for WCAG 2.2 AA compliance — screen reader announcement of page title on client-side navigation _(Rationale: Without RouteAnnouncer, screen reader users get zero feedback on client-side route changes. WCAG 2.2 AA criteria 2.4.2 and 4.1.2 require this. Legally enforceable under the European Accessibility Act (EAA) 2025-2026. The component uses usePathname() + aria-live='polite' + role='status' to announce 'Navigated to [Page Title]' on every route transition.)_ — 2026-06-30
- **Animation Pattern:** Use ProximityTiltWrapper component for ZProximityEngine tiltCard preset on Card-based components _(Rationale: The ProximityTiltWrapper component provides a clean, reusable abstraction around z-proximity-engine's tiltCard preset. It uses an inner wrapper div with transformStyle:'preserve-3d' to avoid transform conflicts with existing CSS hover effects (hover lift, scroll reveals). It skips GSAP/ZProximityEngine entirely in vitest environments (process.env.VITEST check) to avoid jsdom compatibility issues.)_ — 2026-07-01
- **Tooling:** Run npm install in worktree before build; packages may appear in package.json but be missing from node*modules if the worktree was freshly created *(Rationale: The refactor-finish worktree had package.json with all deps listed, but many packages were not in node*modules until npm install was run)* — 2026-07-02
- **Architecture:** The site has 31 named routes (not 38) with one dynamic route /news/[slug] generating 7 slug variants, totaling 42 static pages. Route structure uses a (site) route group. _(Rationale: Current implementation differs from the exhaustive content list in the refactor prompt. The existing routes use different slugs (e.g., /about/history vs /about/vision-mission-values). This is the actual baseline.)_ — 2026-07-02
- **Animation:** Use GSAP with useReducedMotion hook for all scroll-triggered animations. Check prefers-reduced-motion via the useReducedMotion hook before initializing GSAP animations. _(Rationale: The project uses GSAP ScrollTrigger for scroll choreography. All animations must respect prefers-reduced-motion for accessibility. The useReducedMotion hook from WalkerHomepage/hooks provides this check.)_ — 2026-07-02
- **TypeScript:** Create .d.ts declaration files in src/types/ for third-party modules that lack type definitions (e.g., roughjs/bundled/rough.esm.js). _(Rationale: roughjs doesn't ship TypeScript declarations for its ESM bundle. A custom declaration file in src/types/ satisfies the TypeScript compiler without adding @types packages.)_ — 2026-07-02
- **Component Pattern:** Decoration components (RoughBorder, RoughDivider, LottieAnimation) go in src/components/decorations/. They are pure presentation components with no layout awareness. _(Rationale: The project follows a pattern where decorative/presentation components are separate from layout-aware panel components. This keeps concerns separated and makes decorations reusable.)_ — 2026-07-02
